Свой прокси-сервер за 15 минут

Одна команда превращает арендованный VPS в HTTPS-прокси для Routekeeper. Ключ от прокси есть только у вас, а без пароля сервер отвечает как обычный веб-сервер.

Вы арендуете небольшой сервер, запускаете на нём одну команду и получаете собственный прокси. Routekeeper отправляет на него трафик выбранных приложений, а сервер передаёт этот трафик дальше в интернет.

Приложение → Routekeeper → TLS → ваш сервер :443 → интернет
HTTPS-прокси

HTTPS-прокси: HTTP CONNECT внутри TLS на веб-сервере Caddy со сборкой forwardproxy@naive. На Mac, кроме Routekeeper, ничего ставить не нужно.

Защита от сканеров

Без пароля сервер отвечает как обычный веб-сервер с сертификатом Let's Encrypt. Поэтому сканеры не находят открытый прокси и не могут пользоваться им чужими руками.

Сервер ваш

Пароль создаётся на самом сервере. Ни пароль, ни ваш трафик не передаются ни Routekeeper, ни его автору. Куда скрипт обращается при установке — ниже.

Только TCP

Такой прокси передаёт только TCP. UDP приложений, идущих через него, Routekeeper по умолчанию блокирует, и браузеры переходят на TCP. Подробнее — в ограничениях.

Что понадобится

  • Сервер. Арендованный VPS с Debian или Ubuntu. Что именно заказать — ниже.
  • Домен. Свой или бесплатный на DuckDNS: по нему Let's Encrypt выдаёт сертификат. Как его получить — в шаге 1.
  • Mac с Routekeeper. Если Routekeeper ещё не установлен, начните с быстрого старта. Терминал для входа на сервер уже есть в macOS.
  • Около 15 минут. Сама установка на сервере занимает 1–3 минуты.

Какой сервер заказать

VPS — виртуальный сервер, который хостинг сдаёт в аренду помесячно. Подойдёт самый простой тариф. При заказе выберите:

  • Операционная система: Debian 12 или 13, Ubuntu 22.04 или 24.04. На них скрипт проверен.
  • Процессор: x86_64, его также называют amd64, x64 или Intel/AMD. Серверы на ARM (arm64, aarch64) не подойдут: для них нет готовой сборки Caddy с прокси.
  • Память: от 1 ГБ. Диск — самый маленький из предложенных.
  • Адрес: публичный IPv4. Тариф только с IPv6 не подойдёт.
  • Регион: ближайший к вам. Каждое новое соединение через прокси устанавливается примерно за три пинга до сервера, поэтому чем ближе сервер, тем быстрее всё открывается.
  • Виртуализация, если хостер её указывает: лучше KVM. На контейнерных VPS (OpenVZ, LXC) прокси тоже работает, но ускорение BBR там недоступно.

Нужны свободные порты 80 и 443. Если на сервере уже работает сайт, другая VPN-панель или веб-сервер, скрипт ничего не тронет и остановится. Для прокси возьмите отдельный сервер.

Где взять IP и пароль

После оплаты хостер присылает письмо с IP-адресом сервера и паролем пользователя root — главного администратора сервера. Те же данные обычно есть на странице сервера в панели управления хостера. Если пароль root при заказе можно задать самому, задайте длинный случайный.

Некоторые хостеры, чаще облачные, вместо root дают обычного пользователя (например, ubuntu), которому разрешено выполнять команды администратора через sudo. Так тоже можно: команды для этого случая есть в каждом шаге.

Если хостер просит SSH-ключ уже при заказе, создайте ключ на Mac, как в первом шаге защиты сервера, и вставьте в форму его открытую часть. Скопировать её можно командой pbcopy < ~/.ssh/my_server.pub. Входить на сервер тогда нужно с ключом: ssh -i ~/.ssh/my_server root@IP.

1Домен

Прокси нужно доменное имя. На это имя Let's Encrypt выдаёт сертификат, а Routekeeper по сертификату убеждается, что подключается именно к вашему серверу. Имя связывают с сервером A-записью — строкой в DNS вида «имя → IPv4-адрес».

Бесплатный домен на DuckDNS

  1. Войдите на duckdns.org через GitHub, Google или другой предложенный способ.
  2. В поле sub domain впишите имя: латинские буквы, цифры и дефис. Нажмите add domain. Получится адрес вида имя.duckdns.org.
  3. DuckDNS сразу подставляет в поле current ip адрес вашего компьютера. Замените его на IP сервера и нажмите update ip.

Токен DuckDNS не понадобится: IP сервера не меняется, обновлять запись не придётся.

Свой домен

В панели регистратора или DNS-хостинга создайте A-запись: имя — поддомен (или @ для самого домена), значение — IP сервера. Если домен обслуживает Cloudflare, выключите у записи проксирование (серое облако, «DNS only»). Иначе домен будет указывать на адреса Cloudflare, а не на ваш сервер.

Если у домена есть AAAA-запись (IPv6) на другой адрес, удалите её: Let's Encrypt может проверять домен по IPv6, и сертификат не выдадут.

Проверить запись

Запись начинает работать через пару минут. Проверьте на Mac: команда должна напечатать IP сервера.

dig +short имя.duckdns.org

2Вход на сервер

На сервер заходят по SSH из Терминала. Откройте его: Программы → Утилиты → Терминал, или нажмите ⌘Пробел и наберите «Терминал». Подключитесь, подставив IP из письма хостера:

ssh root@IP

Если хостер дал не root, а пользователя с sudo, подставьте его имя:

ssh пользователь@IP

При первом подключении ssh спросит: Are you sure you want to continue connecting (yes/no/[fingerprint])? Так ssh сообщает, что видит этот сервер впервые, и показывает отпечаток (fingerprint) его ключа. Напечатайте yes и нажмите Return. ssh запомнит ключ сервера и предупредит, если по этому адресу когда-нибудь ответит другой сервер.

Затем введите пароль. Символы при вводе не отображаются, так и должно быть; вставить пароль можно через ⌘V. Вход удался, если строка в Терминале сменилась на что-то вроде root@имя-сервера:~#.

Некоторые хостеры при первом входе просят сменить пароль: введите текущий, затем дважды новый.

3Установка

На сервере выполните одну команду, подставив свой домен:

curl -fsSL https://getroutekeeper.app/server.sh | bash -s -- --domain имя.duckdns.org

Если вы вошли не как root, а как пользователь с sudo, добавьте sudo перед bash. sudo может спросить пароль этого пользователя.

curl -fsSL https://getroutekeeper.app/server.sh | sudo bash -s -- --domain имя.duckdns.org

Установка обычно занимает 1–3 минуты. Скрипт по порядку:

  1. проверяет, что на сервере Debian или Ubuntu на x86_64 с systemd, и доставляет недостающие стандартные пакеты;
  2. проверяет, что домен указывает на этот сервер, а порты 80 и 443 свободны; если включён файрвол ufw, открывает в нём эти порты;
  3. скачивает Caddy со сборкой forwardproxy@naive и сверяет её контрольную сумму;
  4. создаёт логин и длинный случайный пароль;
  5. настраивает Caddy: прокси с паролем и простая веб-страница для всех, кто приходит без пароля; сертификат Let's Encrypt Caddy получает и продлевает сам;
  6. включает BBR — алгоритм управления скоростью TCP, который заметно ускоряет соединения на дальних маршрутах;
  7. ставит fail2ban: после пяти неудачных попыток войти по SSH за час адрес не пускается на сервер сутки, при повторах — дольше;
  8. включает автоматические обновления безопасности, сам сервер при этом не перезагружается;
  9. проверяет, что прокси работает с паролем, а без пароля сервер отвечает как обычный веб-сервер, и печатает строку для Routekeeper.

BBR, fail2ban и обновления необязательны. Если сервер их не позволяет, скрипт пишет предупреждение и ставит прокси дальше.

Что вы увидите

Готово. Скопируйте строку и вставьте её в Routekeeper: «Прокси» → ⌘V (или кнопка «Вставить») → «Добавить».

  https://u3f9a1c0b7e42:•••@my-name.duckdns.org:443

Или заполните вручную: тип HTTPS, сервер my-name.duckdns.org, порт 443, логин u3f9a1c0b7e42, пароль •••.
Строка — это ключ от прокси: не публикуйте её. Посмотреть снова: cat /etc/caddy/proxy-credentials

Строки с ==> — этапы, с ✓ — пройденные проверки. Если на сервере включён ufw, после проверки домена появится строка ufw: открыты порты 80 и 443. На этапе «Проверки» скрипт может молчать до нескольких минут, пока Caddy получает сертификат.

Строки с ! — предупреждения: установка продолжается, а в конце, перед «Готово», они повторяются. Строка с ✗ — ошибка, после которой скрипт останавливается. Что делать с каждой, — в разделе Если не получилось.

Прочитать скрипт перед запуском

Скрипт из интернета разумно прочитать до запуска. Исходник открыт: посмотреть скрипт на GitHub. Чтобы запустить ровно тот файл, который прочитали, скачайте его на сервер:

curl -fsSLO https://getroutekeeper.app/server.sh

Просмотрите его. Листайте пробелом, выход — q.

less server.sh

Затем запустите (с пользователем sudo — sudo bash server.sh …):

bash server.sh --domain имя.duckdns.org

Куда обращается скрипт

  • api.ipify.org, а если он не ответил, ifconfig.me — чтобы узнать внешний IPv4 сервера. Через эти же сервисы скрипт в конце проверяет сам прокси.
  • GitHub — чтобы скачать сборку Caddy из релизов проекта klzgrad/forwardproxy. Её контрольная сумма SHA-256 записана в скрипте. Если скачанный файл с ней не совпадает, установка останавливается.
  • Зеркала пакетов Debian или Ubuntu, настроенные на сервере, — чтобы поставить стандартные пакеты: curl, openssl, fail2ban, unattended-upgrades и другие.
  • Let's Encrypt — Caddy получает у него сертификат для вашего домена и потом сам его продлевает.

Сам скрипт скачивается с getroutekeeper.app, больше он к этому сайту не обращается. Логин и пароль создаются на сервере и хранятся только на нём. Ни пароль, ни трафик не передаются ни Routekeeper, ни его автору.

После установки сервер сам обращается только к Let's Encrypt, чтобы продлевать сертификат, и к зеркалам пакетов за обновлениями безопасности.

Флаги и повторный запуск

Запускать команду установки повторно безопасно. Логин и пароль сохраняются, а Caddy перезапускается, только если изменились его программа или настройки; иначе скрипт напишет «Caddy уже настроен, перезапуск не нужен». Флаги добавляются в конец команды.

ФлагЧто делает
--domain имяДомен, A-запись которого указывает на этот сервер. Обязателен для установки.
--new-passwordСоздаёт новые логин и пароль. Старые сразу перестают работать.
--no-bbrНе включает BBR, настройки TCP остаются как есть.
--no-fail2banНе ставит fail2ban.
--no-auto-updatesНе включает автоматические обновления безопасности.
--lang ru, --lang enЯзык сообщений. По умолчанию скрипт берёт его из переменной LANG, а ssh обычно передаёт язык с Mac. Добавьте --lang ru, если сообщения на английском.
--jsonДля скриптов и программ: итог печатается одной строкой JSON.
--uninstallУдаляет прокси; пишется вместо --domain. BBR, fail2ban и обновления остаются.

Флаги --no-… только пропускают шаг. То, что сделал прошлый запуск, они не отменяют.

Подробнее: флаг --json

С --json в стандартный вывод попадает только одна строка JSON, а сообщения о ходе установки и ошибки идут в stderr. Поля: type (всегда https), host, port, username, password, url (та же строка, что без флага), serverIP, caddy (версия) и warnings — массив предупреждений, пустой, если их не было. При ошибке JSON не печатается, а код выхода ненулевой.

Подробнее: что меняется на сервере
  • /usr/local/bin/caddy — Caddy v2.11.2 со сборкой forwardproxy@naive из релизов klzgrad/forwardproxy. SHA-256 архива записан в скрипте.
  • /etc/caddy/Caddyfile — сайт на :443 для вашего домена: TLS 1.2 и 1.3, forward_proxy с basic_auth, hide_ip, hide_via и probe_resistance, file_server со страницей из /var/www/site. Перед установкой файл проверяется командой caddy validate.
  • /etc/caddy/proxy-credentials — логин и пароль, права 600.
  • systemd-сервис caddy от системного пользователя caddy. Сертификаты Caddy хранит в /var/lib/caddy.
  • BBR и очередь fq: /etc/sysctl.d/99-zz-bbr.conf и /etc/modules-load.d/bbr.conf. Префикс 99-zz нужен, чтобы настройки хостера их не перебили.
  • fail2ban: /etc/fail2ban/jail.d/zz-routekeeper.local и /etc/fail2ban/fail2ban.d/zz-routekeeper.local. Бан через nftables: 5 неудачных входов за час — сутки, при повторах срок удваивается до 4 недель. В исключениях — сам сервер и адрес, с которого запущен скрипт (при запуске через sudo этот адрес может туда не попасть).
  • Обновления: пакет unattended-upgrades и /etc/apt/apt.conf.d/20auto-upgrades.

probe_resistance: на запрос к прокси без пароля Caddy отвечает как веб-сервер, а не кодом 407 «нужна авторизация». hide_ip и hide_via: Caddy не добавляет к запросам заголовки Forwarded и Via. Проверки в конце скрипт делает на самом сервере через 127.0.0.1, поэтому они не зависят от того, как хостер маршрутизирует обращения сервера к самому себе.

4Подключение в Routekeeper

В конце скрипт печатает строку вида https://u3f9a1c0b7e42:…@имя.duckdns.org:443. В ней всё, что нужно Routekeeper: тип, сервер, порт, логин и пароль.

  1. Скопируйте строку: в Терминале трижды щёлкните по ней, чтобы выделить её целиком, и нажмите ⌘C.
  2. Вставьте её в Routekeeper.
    • Первый запуск, открыт приветственный экран. На шаге Добавить прокси-сервер нажмите Вставить из буфера. Этот шаг становится доступен после трёх разрешений macOS.
    • Приветствие уже пройдено. Откройте раздел Прокси и нажмите ⌘V или кнопку Вставить под списком.
    Откроется новый прокси с заполненными полями: тип HTTPS, сервер — ваш домен, порт 443, логин и пароль.
  3. Нажмите Проверить. Через пару секунд рядом появится «Работает · … мс · IP …» с IP вашего сервера. Число в миллисекундах — время установки нового соединения, оно обычно втрое больше пинга до сервера.
  4. DNS через прокси и Блокировать UDP и QUIC уже включены, не выключайте их. Нажмите Добавить.
  5. Выберите приложения, которые пойдут через прокси. На приветственном экране для этого есть следующий шаг с кнопкой Выбрать приложения…. Позже — раздел Приложения: нажмите Добавить и выберите приложения из списка установленных. Если прокси у вас один, новые приложения сразу идут через него. Если их несколько, щёлкните маршрут справа в строке приложения и выберите этот прокси. Подробнее — в разделе Приложения и сервисы.

Если вставка не сработала, заполните поля вручную по строке «Или заполните вручную» из вывода скрипта. В поле Сервер должен быть домен, а не IP: по домену проверяется сертификат. Подробнее о полях — в разделе Прокси. Убедиться, что трафик приложений действительно идёт через сервер, поможет проверка на сервере.

Строка — это ключ от прокси. Не публикуйте её и не пересылайте в чаты. Увидеть её снова можно, запустив команду установки ещё раз. Логин и пароль лежат на сервере в /etc/caddy/proxy-credentials.

Защита сервера

Боты круглосуточно подбирают пароли к SSH: на нашем тестовом сервере набиралось около 11 тысяч попыток в сутки. fail2ban не пускает адрес после пяти ошибок, но надёжнее совсем отключить вход по паролю и входить по ключу.

  1. На Mac создайте ключ. На вопрос о passphrase можно дважды нажать Return (ключ без пароля) или задать пароль к ключу. 
    ssh-keygen -t ed25519 -f ~/.ssh/my_server
  2. Передайте серверу открытую часть ключа. Пароль root понадобится в последний раз. 
    ssh-copy-id -i ~/.ssh/my_server.pub root@IP
  3. Войдите по ключу. Если пароль root не спросили, ключ работает. 
    ssh -i ~/.ssh/my_server root@IP
  4. В этой же сессии отключите вход по паролю: 
    printf 'PasswordAuthentication no\nPermitRootLogin prohibit-password\n' > /etc/ssh/sshd_config.d/10-keys-only.conf
systemctl reload ssh
  5. Не закрывая эту сессию, откройте новое окно Терминала (⌘N) и снова войдите командой из шага 3.

Если вы входите как пользователь с sudo, подставьте его имя вместо root в шагах 2 и 3, а в шаге 4 выполните:

printf 'PasswordAuthentication no\nPermitRootLogin prohibit-password\n' | sudo tee /etc/ssh/sshd_config.d/10-keys-only.conf
sudo systemctl reload ssh

Не закрывайте сессию, пока не проверите вход по ключу в новом окне Терминала. Если сервером управляют другие приложения по паролю root, им после этого тоже понадобится ключ. Если доступ всё же потерян, войдите через веб-консоль сервера в панели хостера и удалите файл /etc/ssh/sshd_config.d/10-keys-only.conf.

Подробнее: почему файл называется 10-keys-only

sshd читает файлы из /etc/ssh/sshd_config.d/ по алфавиту и для каждого параметра берёт первое найденное значение. Номер 10 ставит наш файл раньше файлов хостера и cloud-init (например, 50-cloud-init.conf с PasswordAuthentication yes). Проверить действующее значение можно командой sshd -T | grep passwordauthentication: должно быть passwordauthentication no.

Обслуживание

Все команды выполняются на сервере. С пользователем sudo добавляйте sudo в начало команды, а в команде установки — перед bash.

ЗадачаЧто сделать
Обновить Caddy и настройкиЗапустить команду установки ещё раз. Логин и пароль сохранятся, а Caddy перезапустится, только если что-то изменилось.
Снова увидеть строку проксиЗапустить команду установки ещё раз: строка напечатается в конце. Только логин и пароль: cat /etc/caddy/proxy-credentials.
Сменить парольКоманда установки с --new-password: она создаёт новые логин и пароль. Затем в Routekeeper откройте этот прокси в разделе Прокси, впишите их из вывода скрипта и нажмите Сохранить. Маршруты приложений останутся на этом прокси.

Удаление снимает Caddy, его настройки и сертификаты, страницу, логин и пароль. BBR, fail2ban и автоматические обновления остаются: они полезны и без прокси.

curl -fsSL https://getroutekeeper.app/server.sh | bash -s -- --uninstall
Подробнее: как убрать BBR

Удалите /etc/sysctl.d/99-zz-bbr.conf и /etc/modules-load.d/bbr.conf и перезагрузите сервер. fail2ban выключается командой systemctl disable --now fail2ban, автоматические обновления — удалением /etc/apt/apt.conf.d/20auto-upgrades.

Если не получилось

При ошибке скрипт печатает строку с ✗ и останавливается. Исправьте причину и запустите ту же команду ещё раз: уже сделанное скрипт пропустит, а логин и пароль сохранятся. Ниже — каждое сообщение скрипта и что с ним делать.

Запуск

curl: command not found

На сервере нет curl, чтобы скачать скрипт. Поставьте его и повторите команду установки (с пользователем sudo — sudo перед каждой из двух команд):

apt-get update && apt-get install -y curl

bash: --domain: invalid option

В команде пропущены два дефиса после bash -s. Нужно именно bash -s -- --domain …. Скопируйте команду со страницы целиком.

Usage: server.sh --domain NAME …

Скрипт не понял флаг: опечатка, у --domain или --lang нет значения, или у --lang значение не ru и не en. Сверьте команду с таблицей флагов.

«Укажите домен: --domain my-name.duckdns.org»

Домен не указан или записан с ошибкой. Пишите только имя, без https:// и косой черты в конце, латиницей: --domain имя.duckdns.org.

«Запустите от root: … | sudo bash -s -- --domain имя»

Вы вошли как обычный пользователь. Добавьте sudo перед bash, как в подсказке.

«Нужен Debian или Ubuntu, а здесь название ОС.»

На сервере другая система. Переустановите её в панели хостера, выбрав Debian 12 или 13 либо Ubuntu 22.04 или 24.04. Переустановка стирает всё на сервере.

«Нужен systemd.»

Так бывает на контейнерных VPS и в контейнерах Docker. Выберите тариф с виртуализацией KVM.

«Нужен сервер x86_64 (amd64): для aarch64 готовой сборки Caddy с прокси нет.»

Сервер на ARM. Закажите тариф с процессором x86_64 (amd64, Intel/AMD).

«Не удалось установить: пакеты»

Не поставились стандартные пакеты, без которых скрипт не работает. Над этой строкой — сообщение apt о причине. Частые причины: на диске нет места (df -h), недоступны зеркала пакетов, система слишком старая. Выполните apt-get update, исправьте то, на что он жалуется, и запустите скрипт снова.

Скрипт надолго замолчал

На свежем сервере система в первые минуты ставит свои обновления, и скрипт ждёт до 5 минут, пока она закончит. Чаще всего это видно после строки ==> fail2ban для SSH. На этапе ==> Проверки скрипт может ждать несколько минут, пока Caddy получает сертификат. Прерывать не нужно.

Домен и порты

«Не удалось узнать внешний IPv4 сервера. Нужен сервер с публичным IPv4.»

У сервера нет публичного IPv4, или он не может выйти в интернет. Проверьте командой curl -4 https://api.ipify.org: она должна напечатать IP сервера. Если у тарифа только IPv6, закажите у хостера IPv4-адрес или другой тариф.

«A-запись имя должна указывать на IP. Исправьте её у регистратора или в DuckDNS и подождите пару минут.»

Строкой выше скрипт пишет, куда сейчас указывает домен: сервер: IP, имя → адрес, или нет записи, если записи нет вовсе.

  • В DuckDNS проверьте поле current ip: там часто остаётся адрес вашего компьютера.
  • У своего домена в Cloudflare выключите проксирование записи («DNS only»).
  • Если запись только что поменяли, подождите пару минут и проверьте её на Mac командой dig +short.

«Порты 80 и 443 заняты: программы. Похоже, здесь уже работает веб-сервер или другая VPN-панель…»

На сервере уже работает другая VPN-панель или веб-сервер; после двоеточия — названия программ. Скрипт их не трогает. Если они вам нужны, возьмите для прокси отдельный сервер.

Если это ненужный веб-сервер, который хостер поставил вместе с системой (например, apache2), выключите его и запустите скрипт снова:

systemctl disable --now apache2

«На сервере уже есть Caddy со своими сайтами (/etc/caddy/Caddyfile). Скрипт его не трогает: возьмите отдельный сервер.»

Caddy на сервере ставили не этим скриптом, и он обслуживает другие сайты. Скрипт не перезаписывает чужие настройки. Возьмите для прокси отдельный сервер. Если этот Caddy вам точно не нужен, удалите его так же, как ставили, вместе с /etc/caddy/Caddyfile, и запустите скрипт снова.

Caddy и сертификат

Остановился после ==> Caddy v2.11.2-naive с ошибкой curl: (…)

Сервер не смог скачать Caddy с GitHub. Обычно это временная неполадка сети или GitHub. Проверьте командой curl -I https://github.com и запустите скрипт снова через несколько минут.

«Контрольная сумма Caddy не совпала, установка остановлена.»

Скачанный файл отличается от того, контрольная сумма которого записана в скрипте: он повреждён при скачивании или изменён по пути. Caddy не установлен. Запустите скрипт ещё раз позже. Если сообщение повторяется, не отключайте проверку, а сообщите о проблеме.

«В сборке Caddy нет forward_proxy.»

В /usr/local/bin/caddy уже лежит Caddy той же версии, но обычная сборка, без прокси, и скрипт её не заменил. Если этот Caddy больше ничем не используется, переименуйте его и запустите скрипт снова:

mv /usr/local/bin/caddy /usr/local/bin/caddy.old

«Caddy не принял конфигурацию.»

Перед этой строкой — причина от самого Caddy. Со стандартной установкой такого быть не должно. Запустите скрипт ещё раз; если сообщение повторяется, сообщите о проблеме и приложите вывод.

«Caddy не запустился, подробности: journalctl -u caddy -n 50»

Над этой строкой — последние сообщения Caddy, полный журнал покажет journalctl -u caddy -n 50. Частые причины:

  • address already in use — порт 80 или 443 занял другой сервис. Найдите его командой ss -tlnp.
  • На сервере кончилась память или место на диске: проверьте free -m и df -h.

Исправьте причину и запустите скрипт снова.

«Caddy не получил сертификат Let's Encrypt. Чаще всего порты 80 и 443 закрыты в панели хостера (firewall, security group)…»

Строкой выше бывает уточнение: Let's Encrypt: причина.

  • Порты закрыты снаружи. Самая частая причина, особенно с Timeout during connect в уточнении. В панели хостера найдите файрвол (firewall, security group, «сетевые правила») и разрешите входящие TCP 80 и 443. Держите их открытыми и дальше: через них Caddy продлевает сертификат.
  • Домен только что поменяли. Let's Encrypt ещё видит старый адрес или старую AAAA-запись (IPv6). Подождите несколько минут; лишнюю AAAA-запись удалите.
  • Лимит Let's Encrypt, в уточнении rateLimited или too many certificates. Так бывает, если на одно имя много раз ставили и удаляли прокси: удаление стирает сертификат, и каждая установка просит новый. Подождите (от часа до недели, смотря какой лимит) или возьмите на DuckDNS другое имя и запустите скрипт с ним.

Затем запустите скрипт ещё раз.

Проверки

«Прокси с паролем не работает (ответ: '…').»

Сертификат получен, но запрос через прокси с паролем не вернул IP сервера. В скобках — что пришло вместо него.

  • Пусто. Сервер не смог выйти в интернет через прокси: исходящие соединения закрыты у хостера, или api.ipify.org и ifconfig.me временно не ответили (скрипт пробует оба по три раза). Проверьте curl -4 https://api.ipify.org на сервере и запустите скрипт снова через пару минут.
  • Другой IP. У сервера несколько внешних адресов, и наружу он ходит не с того, на который указывает домен. Прокси при этом может работать. Добавьте его в Routekeeper вручную (логин и пароль: cat /etc/caddy/proxy-credentials) и нажмите Проверить.

«Без пароля прокси отвечает 407, а должен отвечать как обычный веб-сервер.»

Скрипт проверяет, что на запрос без пароля сервер отвечает как обычный веб-сервер. Здесь он ответил кодом 407 «нужна авторизация», то есть сообщил, что на нём прокси, и сканеры смогут его найти.

Со стандартной установкой такого быть не должно: обычно это значит, что настройки Caddy меняли вручную. Запустите скрипт ещё раз, он перезапишет настройки. Если сообщение повторяется, сообщите о проблеме.

Предупреждения

Эти строки начинаются с !. Установка после них продолжается, прокси работает. В конце, перед «Готово», они повторяются, а с флагом --json попадают в поле warnings.

«BBR на этом сервере недоступен (так бывает на VPS с контейнерной виртуализацией). Прокси работает и без него.»

На контейнерных VPS (OpenVZ, LXC) ядро общее с хостом, и менять в нём настройки TCP нельзя. Делать ничего не нужно.

На дальних маршрутах одно соединение без BBR может быть заметно медленнее: при пинге около 200 мс — примерно 0,5 МБ/с вместо 3. Если скорость важна, выберите VPS на KVM. Чтобы скрипт не пробовал включать BBR, есть флаг --no-bbr.

«fail2ban не установился, SSH остался без защиты от подбора пароля.»

apt не смог поставить fail2ban; над предупреждением — его сообщение. Прокси это не мешает. Запустите скрипт ещё раз позже или просто отключите вход по паролю: тогда подбирать нечего.

«fail2ban не принял конфигурацию, SSH остался без защиты от подбора пароля.»

Установленная версия fail2ban не приняла настройки скрипта. Скрипт убрал свои файлы, чтобы fail2ban не перестал запускаться. Причину покажет fail2ban-client -t. Надёжная замена — вход только по ключу.

«fail2ban не запустил защиту SSH (journalctl -u fail2ban покажет почему).»

fail2ban установлен, но защиту SSH не включил. Так бывает на контейнерных VPS, где fail2ban не может управлять файрволом. Посмотрите journalctl -u fail2ban -n 50. Надёжная замена — вход только по ключу.

«unattended-upgrades не установился, обновления безопасности придётся ставить вручную.»

Автоматические обновления не включились. Запустите скрипт ещё раз позже или время от времени ставьте обновления сами: apt update && apt upgrade.

Удаление

«Запустите от root.»

Вы вошли как обычный пользователь. Добавьте sudo перед bash: … | sudo bash -s -- --uninstall.

«Caddy на этом сервере ставил не Routekeeper, удалять его скрипт не будет.»

В настройках Caddy нет прокси Routekeeper: это чужой Caddy, со своими сайтами. Скрипт его не удаляет. Если он вам не нужен, удалите его так же, как ставили.

Вход на сервер

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

Ключ сервера изменился. После переустановки системы на сервере так и должно быть. Удалите старый ключ на Mac и подключитесь снова:

ssh-keygen -R IP

Если систему вы не переустанавливали, не продолжайте и уточните у хостера, что произошло.

Permission denied

Неверный пароль или имя пользователя. Проверьте их в письме хостера. Если хостер запретил вход root по паролю, войдите пользователем, которого он дал, и пользуйтесь sudo.

Connection refused или Operation timed out

Сервер ещё загружается, IP набран с ошибкой, или fail2ban не пускает ваш адрес после нескольких неверных паролей. В последнем случае подождите сутки или войдите через веб-консоль в панели хостера и снимите бан: fail2ban-client set sshd unbanip ваш IP.

В Routekeeper

Проверить показывает ошибку

В поле Сервер должен быть домен, а не IP, а строка должна быть вставлена целиком. Что значит каждое сообщение проверки, — в разделе Если не работает.

Медленно

Выберите сервер ближе. С BBR на маршруте с пингом около 200 мс одно соединение даёт примерно 3–4 МБ/с.

Прокси нестабилен в вашей сети

Можно поставить на тот же сервер другой прокси и подключаться к нему через локальный SOCKS5-клиент, например sing-box или Xray. Как подключить такой клиент к Routekeeper, — в разделе Прокси.

Если застряли, откройте issue на GitHub и приложите вывод скрипта. Строку прокси и пароль из него удалите.
