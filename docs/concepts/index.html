Как это работает

Routekeeper решает судьбу каждого соединения отдельно. Здесь — из чего он состоит, в каком порядке выбирает действие и что происходит с DNS и UDP.

Чтобы пользоваться Routekeeper, эту страницу читать не обязательно: хватит быстрого старта. Она нужна, когда хочется понять, почему соединение пошло именно так, а не иначе.

Из чего состоит Routekeeper

Routekeeper — это две программы, которые работают вместе.

Приложение

Окно и значок в строке меню. Здесь вы добавляете прокси и приложения, пишете правила, смотрите монитор. Приложение можно закрыть: маршруты от этого не перестают работать.

Сетевое расширение

Часть Routekeeper, которая встраивается в macOS; сама macOS называет такие модули системными расширениями. Расширение видит каждое новое исходящее соединение, решает, что с ним делать, и отправляет трафик через прокси. Работает и при закрытом окне, и после перезагрузки.

Сетевое расширение хранит прокси, пароли и правила в файле, который может читать только система. Окно получает настройки без паролей, а проверку прокси выполняет само расширение.

Почему macOS просит три разрешения

Внутри расширения две половины, и на каждую macOS спрашивает отдельно. Плюс разрешение на установку самого расширения.

РазрешениеЧто оно даётБез него
Сетевое расширениеУстановить расширение в систему.Не работает ничего.
Фильтрация сетевого контентаФильтр видит каждое новое исходящее соединение: какое приложение и куда подключается. Он пропускает соединение, блокирует его или придерживает, пока вы отвечаете на вопрос. Он же записывает соединения в монитор.Нет файрвола, монитора и окон вопроса.
Конфигурация проксиПрокси-часть забирает соединения, которым положено идти через прокси, и передаёт их на ваш прокси-сервер.Ничего не идёт через прокси.

Как дать разрешения в macOS 14 и macOS 15, написано в быстром старте.

Подробнее: устройство для опытных
  • Фильтр — это NEFilterDataProvider на уровне сокетов: он решает судьбу соединения при открытии и не читает передаваемые данные. Прокси-часть — NETransparentProxyProvider, она принимает исходящие TCP и UDP.
  • Перехватываются только исходящие соединения. Входящие Routekeeper не трогает.
  • Настройки лежат в /Library/Application Support/Routekeeper, папка доступна только root. Версии 0.2.x хранили их в /Library/Application Support/AppProxy.
  • Прокси-конфигурация включается по требованию, поэтому после перезагрузки или остановки macOS запускает её снова сама.
  • Решение принимается один раз, когда соединение открывается. Если поменять правило, уже открытые соединения остаются там, где были; новые пойдут по-новому.

Как решается судьба соединения

Для каждого нового соединения Routekeeper знает три вещи: какое приложение подключается (по его подписи), куда (имя сайта, если оно известно, IP-адрес и порт) и как (TCP или UDP). Дальше он идёт по шагам сверху вниз и останавливается на первом, который даёт ответ.

Шаги по порядку

  1. Routekeeper выключен — всё идёт напрямую, как будто его нет. Переключатель Routekeeper включён есть в меню значка и внизу боковой колонки окна.
  2. Правило для адреса. Сюда относятся правила из раздела Правила (домен, IP-адрес, подсеть, порт, протокол) и сервисы из раздела Приложения. Если подходит несколько, побеждает самое точное: точный адрес важнее *.домена, домен важнее подсети, а при одинаковом адресе правило с портом важнее правила без порта. Порядок строк в списке не играет роли. Разобранные примеры — на странице «Правила».
  3. Маршрут приложения — то, что выбрано для приложения в разделе Приложения. Он действует на весь трафик приложения, который не забрали более точные правила. Если включено Вместе с дочерними процессами, маршрут действует и на его дочерние процессы — программы, которые приложение запускает. Если у такой программы есть свой маршрут, важнее её собственный.
  4. Режим по умолчанию — что делать с соединением, для которого нет ни правила, ни маршрута. В режиме Только прокси (он стоит сразу после установки) такое соединение идёт напрямую. Остальные режимы описаны на странице «Режимы файрвола».

Пример

Браузер добавлен в Приложения с маршрутом через прокси «Амстердам». В разделе Правила есть правило «любое приложение · *.corp.example → Напрямую» для корпоративного портала. Терминал никуда не добавлен, режим — Только прокси.

СоединениеЧто сработалоИтог
Браузер → portal.corp.exampleШаг 2: правило для *.corp.example точнее, чем маршрут браузераНапрямую
Браузер → example.orgШаг 3: маршрут браузераЧерез «Амстердам»
Терминал → example.orgШаг 4: правила и маршрута нет, режим Только проксиНапрямую
Терминал → portal.corp.exampleШаг 2: правило для любого приложенияНапрямую
Подробнее: точный порядок для опытных
  • До правил. Если Routekeeper выключен, соединение идёт напрямую и не записывается в монитор. Соединения с самим прокси-сервером (его адрес и порт из списка Прокси) всегда идут напрямую, иначе до прокси было бы не достучаться.
  • Встроенные правила с источником По умолчанию: 127.0.0.0/8 и ::1 → Напрямую, сам Routekeeper → Напрямую (это его проверки прокси). Они участвуют в выборе наравне с вашими.
  • Сравнение правил. Из включённых правил, подходящих по приложению, адресу, порту и протоколу, выбирается одно. Сравнение идёт по очереди: точность адреса (точное имя или IP, затем *.домен — чем длиннее, тем точнее, затем подсеть — чем длиннее префикс, тем точнее, затем «любой адрес»); вписанный вручную адрес важнее сервиса с той же точностью; правило с портом важнее; правило с протоколом важнее; точное приложение важнее его дочерних процессов, а те важнее «любого приложения»; при полном равенстве — Блокировать, затем Через прокси, затем Напрямую, затем Спрашивать.
  • Маршрут приложения — это тоже правило: приложение и «любой адрес» без порта и протокола. Поэтому он проигрывает любому правилу с адресом, портом или протоколом и выигрывает у правила «любое приложение · любой адрес».
  • Без имени сайта правила по доменам не срабатывают: соединение по голому IP подходит только под правила с IP и подсетями. В некоторые сервисы входят подсети (например, адреса Telegram), они срабатывают и по IP. Подробнее — в ограничениях.
  • Без правила, если включено Настройки → Сеть → Не трогать localhost (включено по умолчанию), соединения с самим Mac идут напрямую. Затем срабатывает режим. В режиме Спрашивать до окна вопроса ещё действуют автоматические разрешения для программ Apple и программ, установленных до Routekeeper.
  • Правила со сроком из окна вопроса («Пока работает…») исчезают, когда процесс завершается.

Что происходит после решения «Через прокси»

TCP-соединение уходит на прокси-сервер. Если прокси недоступен, соединение обрывается с ошибкой и напрямую не уходит. Так Routekeeper не раскрывает ваш адрес, когда прокси упал: это называют fail-closed. Если вам важнее, чтобы приложения работали хоть как-то, включите Настройки → Сеть → Если прокси недоступен — пускать напрямую (по умолчанию выключено).

С UDP всё иначе: через прокси он не идёт вовсе. Что с ним происходит, описано ниже, в разделах про DNS и про UDP.

Четыре действия

У правила, маршрута приложения и сервиса одно из четырёх действий.

ДействиеЧто происходит с соединениемЗаметки
Через проксиИдёт через выбранный прокси-сервер. Сайт видит IP прокси, а не ваш.В списках показывается именем прокси, например Прокси: Амстердам. Через прокси идёт только TCP.
НапрямуюИдёт через ваше обычное подключение, как без Routekeeper.Так по умолчанию идут все приложения, которые вы не добавили.
БлокироватьСоединение сразу обрывается. Приложение видит ошибку сети.При равной точности блокирующее правило важнее остальных.
СпрашиватьСоединение ждёт, пока вы ответите в окне вопроса: Заблокировать, Через прокси или Разрешить.Без ответа через 60 секунд соединение разрешается (оба значения меняются в Настройки → Файрвол). Если приложение Routekeeper не запущено, спросить некому: соединение разрешается, а для приложения создаётся разрешающее правило с пометкой На проверку. Для сервисов этого действия нет.

Ответ в окне вопроса сохраняется как правило: навсегда или пока работает программа. Вариант Один раз правила не сохраняет. Подробно — на странице «Режимы файрвола».

DNS: как приложения узнают адрес сайта

Сайты в интернете находятся по числовым адресам — IP. Людям и программам удобнее имена, например example.com. DNS — справочная служба, которая переводит имя в адрес. Обычно на такие запросы отвечает ваш провайдер или роутер, поэтому он видит, какие имена спрашивает ваш Mac.

Что делает «DNS через прокси»

Переключатель DNS через прокси есть у каждого прокси и по умолчанию включён. Когда приложение подключается к сайту по имени, Routekeeper передаёт прокси само имя, а не адрес. Прокси-сервер сам узнаёт адрес и подключается к нему. Сайт открывается так же, как если бы вы открывали его с сервера.

Выключать переключатель обычно незачем. Без него прокси получает IP-адрес, который узнал ваш Mac.

Что при этом идёт мимо прокси

  • Соединение без имени. Если приложение подключается сразу по IP-адресу, прокси получает только адрес: узнавать нечего. Правила по доменам к такому соединению тоже не подходят.
  • DNS-запросы самого приложения. Некоторые приложения, например браузеры и мессенджеры, сами отправляют DNS-запросы по UDP на порт 53. У приложения с маршрутом через прокси такие запросы идут напрямую. Routekeeper их не блокирует, чтобы приложение не сломалось, а только отмечает в разделе Мимо прокси как «DNS мимо прокси».
  • Запросы системной службы имён. Часто адрес за приложение узнаёт сама macOS. Такие запросы Routekeeper не может отнести к конкретному приложению и не показывает.

Для браузера включите «DNS через HTTPS». Этот параметр есть в настройках Chrome, Edge, Firefox и Brave. С ним браузер спрашивает адреса внутри обычного HTTPS-соединения (DoH), и если браузер целиком идёт через прокси, эти запросы тоже пойдут через прокси. Порт 53 браузеру не блокируйте: без DoH он перестанет открывать сайты.

Подробнее: что считается DNS и где это видно
  • DNS-запросом Routekeeper считает соединение на порт 53 или 853. Если такое соединение по UDP идёт от приложения, которому положено идти через прокси, оно уходит напрямую при любом положении Блокировать UDP и QUIC и отмечается как «DNS мимо прокси». Это наименее важный вид пометок.
  • Заблокировать его можно только явным правилом: кнопка Блокировать DNS в разделе Мимо прокси создаёт правило «приложение · порт 53 → Блокировать». Для браузеров кнопки нет: им нужен DoH.
  • Служебные имена ipv4only.arpa и _dns.resolver.arpa не отмечаются: их спрашивают все системы одинаково, и они ничего о вас не говорят.
  • Пометки зависят от того, куда по правилам должно было идти само соединение. Процесс мимо правила отмечается только у приложений, у которых весь маршрут идёт через прокси. DNS и UDP отмечаются, когда это соединение по правилам должно было уйти в прокси. Поэтому браузер, у которого через прокси идут только отдельные сервисы или домены, почти не проверяется: его DNS-запросы обращаются к адресу DNS-сервера, а не к этим доменам. Подробнее — что замечает Routekeeper.
  • С включённым переключателем SOCKS5-прокси получает в запросе на подключение имя хоста, HTTP и HTTPS-прокси — имя в запросе CONNECT. С выключенным — IP-адрес.
  • В режиме Спрашивать есть отдельная настройка Разрешать DNS-запросы (UDP 53): она пропускает без вопроса DNS-запросы приложений без правила. По умолчанию выключена.

UDP и QUIC

Данные по сети ходят двумя основными способами. TCP похож на разговор с подтверждением: стороны договариваются о соединении и проверяют, что всё дошло. На нём работают сайты, почта и большинство приложений. UDP похож на открытки без подтверждения: быстрее, но без гарантий. По UDP идут звонки, видео в реальном времени, игры, DNS и QUIC — новый способ загружать сайты, которым пользуются браузеры.

Прокси типов SOCKS5, HTTP и HTTPS в Routekeeper передают только TCP. Значит, UDP приложения, пущенного через прокси, через прокси пройти не может. Что с ним делать, решает переключатель Блокировать UDP и QUIC в настройках прокси.

ПереключательЧто происходит с UDPЧто вы заметите
Включён (по умолчанию)UDP блокируется.Браузеры сами переходят на обычный HTTPS по TCP и работают через прокси. Звонки и голосовые чаты могут не работать — см. ограничения.
ВыключенUDP идёт напрямую, мимо прокси.Каждое такое соединение отмечается в разделе Мимо прокси как «UDP мимо прокси».

Исключение — DNS по UDP. Он идёт напрямую и только отмечается при любом положении переключателя, как описано выше.

Почему правило для сервиса может не поймать QUIC

Правила по доменам и сервисам узнают сайт по имени. В UDP-соединении, в том числе в QUIC, имени сайта обычно нет — только IP-адрес. Такое соединение не подходит под правило домена и идёт по маршруту приложения.

Пример: браузер идёт напрямую, а сервис YouTube из списка Сервисы — через прокси. Видео по QUIC уйдёт напрямую: для Routekeeper это просто UDP-соединение браузера на порт 443. Помогает правило «браузер · порт 443 · UDP → Блокировать». QUIC перестаёт работать, браузер переходит на TCP, где имя сайта известно, и правило сервиса срабатывает. Готовая настройка — в рецепте про видео в браузере.

Подробнее: как Routekeeper обрабатывает UDP
  • Фильтр видит исходящие TCP и UDP, прокси-часть принимает и то и другое. Если для UDP-соединения выбрано Через прокси: DNS (порты 53 и 853) уходит напрямую с пометкой; остальное при включённом Блокировать UDP и QUIC закрывается, при выключенном — уходит напрямую с пометкой «UDP мимо прокси».
  • Переключатель задаётся для каждого прокси отдельно и действует на приложения, которые идут через этот прокси.
  • Кнопка Блокировать UDP в разделе Мимо прокси включает этот переключатель у прокси, через который идёт приложение. Если у приложения нет маршрута через прокси, кнопка создаёт правило «приложение · UDP → Блокировать».
  • Правила с действием Блокировать и Напрямую действуют на UDP так же, как на TCP.
