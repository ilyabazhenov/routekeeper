Checking and monitoring: where each connection went

Routekeeper shows what goes through the proxy, what goes direct and what went around it. Start with the one-minute check, and for full certainty, compare with your own server.

There are five places to check, from simple to detailed.

Menu bar

Whether the proxy works and which IP websites see.

Overview

The main thing in one line, and what to do about it.

Monitor

Every connection: which app, where to, and by which route.

Leaks

What went direct from apps that should go through the proxy.

Your server

An independent check: whether connections from your Mac arrive.

The one-minute check

  1. Click the Routekeeper icon in the menu bar. If everything works, there is a green status line under the name, and below it a line like IP 203.0.113.10 · NL. This is the external IP that websites see when traffic goes through the main proxy (the one most apps go through), and the country code. While the check is running, the line says Checking IP….
  2. Compare this address with your usual one: they should be different. If the proxy is your own server, you’ll see the server’s IP.
  3. Check the app itself. In a browser that goes through the proxy, open any page that shows your IP. In Terminal, if it goes through the proxy, run the command below. The address should match the IP in the menu bar. 
    curl https://ipinfo.io/ip
  4. If there is no IP line, the status line is orange or gray. Open Overview: it says what happened and what to do.

The IP in the menu bar shows that the proxy works. It doesn’t prove that a specific app goes through the proxy. For that, use step 3 or the monitor.

You can also check each proxy on its own: the Proxy section, the Check button. It shows “Working”, the latency and the external IP, or the error text. For details, see Checking on the Proxies page.

Details: where the IP and latency come from

Routekeeper itself opens a connection through the proxy to the ipinfo.io service on port 80 and asks for the external address and country. The latency is the time it takes to open a connection through the proxy. This takes several round trips to the server, so for a distant server that works fine, 500–800 ms is normal.

The menu bar rechecks the main proxy when you open it, but no more than once a minute. While the main proxy is unreachable, it’s rechecked once a minute on its own. What else Routekeeper sends over the network is described on the Privacy page.

Overview

The main screen of the Routekeeper window, ⌘1. At the top is one line about the most important thing. Below it are what’s waiting for your answer, the routes, the counters and what’s going through the proxy right now.

The headline: what happened and what to do

The headline always shows the most serious problem. In the table, the states go from most to least serious.

One exception: if Settings → Network → If the proxy is down, go direct is on, connections go direct when the proxy is unreachable, but the headline won’t say so.

In version 0.2.1, any leak, including DNS, showed the Leaks detected headline, and there was no separate headline for DNS.

Below the headline

Lines appear here when there is something to do:

  • Connections around the proxy in the last hour (or Direct DNS queries in the last hour, if there were only those), with the app that has the most of them. The Details button opens the Leaks section.
  • Waiting for answer: N: in Ask mode, programs are waiting for your decision. The Answer button brings the prompt forward. For details, see Ask mode.

Routes

There is one row for each proxy that routes go through. The last row is Direct: everything else goes through your usual connection.

  • Dot: green means the proxy answers, orange means it answers slowly, red means it doesn’t answer, and gray means it hasn’t been checked yet.
  • Name, country and external IP from the last check.
  • Latency. From 1500 ms, “slow” is added to it. For a distant server that works fine, 500–800 ms is normal.
  • What uses the route: icons and names of apps and services. Click to expand the full list. Clicking an item opens its rule in the Apps or Rules section.
  • Speed right now and, if you have several proxies, each one’s share.
  • The “…” menu: Check Again, Move Routes To (moves only this proxy’s routes), All Proxies….

If a proxy doesn’t answer, its row is highlighted, and there are two buttons below it: Move to “…” (to another proxy, if possible one that passed its check) and Check Again. Check All is in the window’s toolbar, and the All Proxies link is next to the Routes heading. While Overview is open, Routekeeper rechecks the proxies used in your routes, but each one no more than once a minute.

To move all apps to another proxy in one go, use the panel at the bottom of the sidebar or the menu of the menu bar icon (there, if you have two or more proxies). For details, see Switching to another proxy.

Counters and “Through Proxies Now”

  • The Leaks card: how many leaks there were, since when they’ve been counted, and which one was the last. The Details link goes to the section.
  • The traffic card: the speed through the proxy right now, how much has been transferred since counting started, and a graph for the last 3 minutes. A Monitor link.
  • Through Proxies Now: apps that sent data through the proxy in the last minute, the most active at the top. For each app: which service’s rule sent it to the proxy, which proxy it uses (if you have several), how many connections it has and its speed. Apps that go through the proxy only by a service rule also show up here. The first five are shown, and the rest are in the monitor.

Monitor

A list of connections: which app, where to, and by which route. Open Monitor in the sidebar (⌘5) or in the menu of the menu bar icon.

The counters are filters

At the top are five cards: Through Proxy, Direct, Blocked, Leaks, Errors. Each shows a number and its share of all connections. Click a card, and only those connections stay in the list. Click it again to show all of them. Next to them is the Proxy Traffic card: the speed right now and how much has gone through the proxy since counting started.

The search field in the toolbar searches by domain, IP and app name.

Three views

Use the switch at the top of the window. The filter and search work in all three views.

  • Connections: a table with the columns App, Host, Route, ↑ / ↓, Time. The Protocol column is hidden: to show it, right-click the table header. The Route column shows the proxy’s name, Direct, Blocked, Error, Waiting or the kind of leak. The amount of data is counted only for connections through the proxy. The table shows the last 500 connections found. If there are more, “showing the last 500” appears under the window title.
  • By App: a summary for each app. How many connections it has, how many go through the proxy, direct and blocked, how many problems (leaks and errors), its traffic and the last address. Double-click a row, or choose Show Connections in the row’s menu, to open this app’s connections.
  • Map: where in the world your traffic goes. More about it below.

A connection row

Select a row, and a panel with details appears below the table: IP, process number (PID), Decision (why the connection went this way: which rule, the mode, an automatic permission), Duration. For connections through the proxy, there are also Proxy latency and Traffic. For an error, the panel gives its cause; for a leak, a tip.

The buttons on the panel:

  • Create Rule… opens the rule editor, already filled in with this app and address.
  • Through “…” adds a rule right away: this app and this address through the main proxy.
  • Block Host adds a rule right away that blocks this address for this app.

Right-click a row to open a menu: Create Rule…, Block This Host, This Host Through “…”, Copy Host, Copy IP. For several rows: Copy Hosts or ⌘C.

Pause, export and clearing

  • Pause stops updating the list, so it’s easier to read. The counters keep counting. The Resume button turns updates back on.
  • Export saves to a CSV file all connections that match the current filter and search, not only the 500 shown. The columns are time, app, process, host, ip, port, protocol, route, bytes_up, bytes_down.
  • Clear empties the list and resets all counters, including Leaks and the “since …” time in Overview.

Map

  • Lines go from this Mac to the countries the connections go to. Connections through the proxy are drawn via the proxy’s country. The colors: green for through the proxy, blue for direct, red for leaks, orange for errors, gray for blocked.
  • The Mac’s location is worked out from its time zone.
  • The All Apps menu leaves one app on the map. By traffic and By connections change the size of the markers. The amount of traffic is known only for connections through the proxy.
  • Zoom: ⌘+ to zoom in, ⌘− to zoom out, ⌘0 for the whole world.
  • Next to the map is a list of countries. Global networks and Local network and other have rows of their own. Content delivery networks answer from the point nearest to you, and the country in the database is only where they’re registered, so they aren’t on the map.
  • The country database is built into the app. Addresses for the map aren’t sent anywhere.
Details: what is stored, and how much
  • The network extension keeps the last 5000 connections in memory and doesn’t write them to disk. After the extension or the Mac restarts, the list starts over.
  • The counters count from the moment the extension started or from the last Clear.
  • While the Routekeeper On switch is off, connections aren’t recorded.
  • The Direct counter also includes leaks: they went direct too. The Direct filter doesn’t show them; they’re in the Leaks filter.

Leaks

The Leaks section, ⌘6. It shows connections from apps that should go through the proxy but went direct. If there are none, the section is empty and says No Leaks.

Rows are grouped by process and kind, so two helpers of one app show up as two rows with the same name. Each row shows the app, the kind, how many times it happened (× N), up to four addresses, a tip and a fix button. The most serious are at the top.

KindWhat happenedFix button

It’s usually a helper process, when Include Child Processes is off.Through “…” adds a rule: this process through the main proxy. Or turn on Include Child Processes.
UDP around the proxy
orange		The app’s UDP traffic went direct because Block UDP and QUIC is off for its proxy. Most often it’s QUIC in a browser, or calls.Block UDP turns on Block UDP and QUIC for this app’s proxy. If the proxy can’t be determined, it adds a rule that blocks UDP for this process. After that, the app switches to TCP, and calls over UDP stop working. See UDP: calls, voice and games.

Browsers: DNS over HTTPS instead of blocking

If you close port 53 for a browser, it will stop opening sites. That’s why browsers don’t get the Block DNS button. Instead, turn on “DNS over HTTPS” (DoH) in the browser itself. Then the browser looks up site addresses inside an ordinary HTTPS connection, and that connection goes through the proxy along with the rest of the traffic.

BrowserWhere to turn it on
ChromePaste chrome://settings/security into the address bar. Turn on “Use secure DNS” and choose a provider from the list, not your current one.
Edgeedge://settings/privacy → the “Security” section → “Use secure DNS to specify how to look up the network address for websites”. Choose a provider from the list.
Firefoxabout:preferences#privacy → “DNS over HTTPS” → under “Enable secure DNS using”, choose “Increased Protection” or “Max Protection”.
Bravebrave://settings/security → “Use secure DNS”. Choose a provider from the list.

The names depend on the browser version. If you can’t find the setting, type “DNS” in the settings search. After you turn it on, restart the browser, and new DNS around the proxy rows will stop appearing for it. For step-by-step instructions, see the recipe DNS over HTTPS in the browser.

Details: which DoH option is more reliable, and which browsers are recognized
  • With the current-provider option in Chrome, Edge and Brave, and with “Default Protection” or “Increased Protection” in Firefox, the browser may fall back to ordinary DNS if secure DNS isn’t available. “Max Protection” in Firefox and a provider chosen from the list in Chrome, Edge and Brave don’t do this.
  • Routekeeper treats these apps as browsers: Chrome (all channels), Chromium, Edge (except Canary), Brave, Arc, Vivaldi, Opera, Firefox (including Developer Edition and Nightly), Zen, Waterfox and Yandex Browser.
  • Safari looks up addresses through the macOS system service, so its DNS queries don’t show up in Leaks.
  • The service queries ipv4only.arpa and _dns.resolver.arpa are the same for everyone and say nothing about you. Routekeeper doesn’t flag them.

Notifications

In Settings → General → Notifications, there are two switches, and both are on: About leaks around the proxy and About connections the proxy couldn’t make. So as not to flood you with messages, Routekeeper sends at most one notification every 10 minutes for each kind of problem in a given app.

Notifications arrive while the Routekeeper app is running, even if its window is closed. macOS asks for permission to show them at first launch. If you declined, turn them on in System Settings → Notifications → Routekeeper.

What Routekeeper notices and what it doesn’t

Routekeeper checks only apps whose whole traffic goes through the proxy, that is, apps with the Through Proxy route in the Apps section. If an app is set to go direct, or goes through the proxy only for certain addresses, Routekeeper treats that as your decision, not as a mistake.

SituationNoticed?What you see
An app with a route through the proxy sends a DNS query over UDP by itself (port 53 or 853)YesDNS around the proxy. The query goes direct: Routekeeper flags it but doesn’t block it until you add a rule.
UDP or QUIC from such an app when Block UDP and QUIC is offYesUDP around the proxy.
The same when Block UDP and QUIC is on (the default)Not flaggedUDP is blocked and shown as Blocked in the monitor.
A process from the same app or the same developer isn’t covered by the rule and connects directly over TCPYesProcess outside the rule.
A browser or app goes through the proxy only by domain or service rules, and its own route is DirectNoIts DNS, QUIC and all other addresses go direct as part of its usual route. You can close QUIC with a rule; see the recipe One video service in the browser through a proxy.
Name lookups that the macOS system service makes on behalf of an app (this is how most programs and Safari work)NoThe service sends them, not the app, and Routekeeper doesn’t link them to the app.
Apple push notifications (the apsd system process)No, and that’s normalapsd is a separate macOS process, and it goes direct. It isn’t the app’s own traffic.
A program from another developer that the app starts, when Include Child Processes is offNoIt follows its own route or the mode.
Connections in the first seconds after the extension restarts or updatesNoThe extension doesn’t see them. See Pause when the extension restarts.
The Routekeeper On switch is offNoEverything goes direct, and the monitor doesn’t record anything.
Connections to the proxy server itself and inside the MacNot countedThat’s as it should be.
Details: the exact checking rules
  • Which app counts as “through the proxy”. Routekeeper takes the rule that would apply to an arbitrary TCP connection from this app to an unknown address. If that rule leads through a proxy, the app is checked. This can be the app’s route or a general “any app → proxy” rule.
  • DNS means ports 53 and 853. Over UDP, such queries don’t go through the proxy: proxies carry only TCP. DNS over HTTPS is an ordinary HTTPS connection to port 443. It goes through the proxy and doesn’t count as a leak.
  • Process outside the rule is checked only for TCP and only for “whole app → proxy” rules. The process must be inside this app’s bundle. If the rule is for a command-line program, any other command-line program from the same developer (Team ID) counts.
  • History. The section shows the connections that are still in the monitor. The counter in Overview also remembers older ones, until you click Clear or the extension restarts.

Checking on your own server

The most independent check is to look on the server and see whether connections from your Mac arrive. The commands below are for a server set up with the Your own proxy server guide: there, the proxy is Caddy on port 443.

  1. Find out your usual address. In a browser that goes direct (for example, Safari, if you haven’t routed it through the proxy), open any page that shows your IP. Write it down.
  2. Connect to the server over SSH, the same way as during installation.
  3. Look at the open connections to Caddy on port 443: 
    ss -tnp state established '( sport = :443 )'
    The Peer Address:Port column shows the addresses the connections came from. Your address from step 1 should be among them, and the last column should mention caddy. The address may be written as [::ffff:198.51.100.7]:51234; it’s the same IPv4 address.
  4. Count the connections from your address only, and watch how the number changes. Put in the address from step 1: 
    watch -n 2 "ss -tn state established '( sport = :443 )' | grep -c YOUR_IP"
    On your Mac, open an app that goes through the proxy and start using it: the number goes up. Close the app, and the number goes down as its connections close. To exit watch, press Ctrl+C.

Keep in mind that Routekeeper itself checks the proxy through this same server, so one or two connections may show up even when your apps are closed.

On the Mac

Open Terminal and look at the open connections to the server. Put in the server’s IP:

netstat -an -p tcp | grep ESTABLISHED | grep 'SERVER_IP.443'

Each line is one connection to the proxy. macOS writes the port after a dot: 203.0.113.10.443. If the server is entered as a domain in Routekeeper, find out its IP:

dig +short DOMAIN
Details: which process holds these connections

Connections to the proxy are opened by Routekeeper’s network extension on behalf of the apps, so the app names don’t appear here. To see which app went where, use the monitor. To see the process, you need an administrator password:

sudo lsof -nP +c 0 -iTCP@SERVER_IP:443 -sTCP:ESTABLISHED

The COMMAND column will show a process whose name starts with Routekeeper. If you see a different program there, something else is also connecting to the server, for example a proxy client.
