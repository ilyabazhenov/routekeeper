Proxies: where to send traffic

A proxy is the server Routekeeper sends the traffic of your chosen apps through. This page covers how to add a proxy, check it and, if needed, replace it with another one.

Routekeeper has no servers of its own. It sends app traffic to the proxy you give it: your own server, a client of another program on this Mac, a work proxy or a proxy from a provider.

App → Routekeeper → proxy → site

Don’t have a proxy? Routekeeper can set one up on a rented server by itself: all it needs is the server’s IP and password. See Your own proxy server.

Which type to choose

Routekeeper works with three types of proxy. The type sets how Routekeeper talks to the server. Apps don’t notice the difference.

TypeDefault portWhen to choose itWhat to know
SOCKS51080A sing-box, Xray or Clash client on this Mac. A proxy from a provider with a line like socks5://….The connection to the proxy isn’t encrypted: the login, password and site names can be seen on the way.
HTTP8080A work proxy in the office. A proxy with a line like http://….The connection to the proxy isn’t encrypted. Only login-and-password sign-in.
HTTPS443Your own server, set up with our guide. A proxy with a line like https://….The connection to the proxy is encrypted with TLS. The Server field needs a domain name.

How to choose:

  • You have a proxy line from a provider or from the server install script: just paste it, and the type is set for you.
  • Your own server set up with our guide: HTTPS.
  • A client on this Mac: SOCKS5, server 127.0.0.1. See Local client for details.
  • A proxy at work: HTTP, or HTTPS if your IT department says so. See Work proxy for details.
  • A remote server, and you have a choice: take HTTPS. SOCKS5 and HTTP also work over the internet, but the login, password and site names travel in plain text. The content of HTTPS sites stays encrypted in any case.

Routekeeper doesn’t support other protocols, such as Shadowsocks or VLESS, directly. If your server uses such a protocol, run its client on the Mac and connect Routekeeper to the client’s local port, as described below.

Details: how Routekeeper talks to each type of proxy
  • SOCKS5: as in RFC 1928, with login and password as in RFC 1929. Only the CONNECT command is used, so only TCP. Routekeeper doesn’t use UDP ASSOCIATE, so UDP doesn’t go through SOCKS5 even if the client supports it.
  • HTTP: for each connection, a tunnel is opened with the CONNECT method, including to port 80. The login and password are sent in the Proxy-Authorization: Basic header.
  • HTTPS: the same CONNECT inside TLS 1.2 or newer, ALPN http/1.1. The server certificate is checked against the macOS trusted root certificates and the name in the Server field. A self-signed certificate won’t pass the check.
  • Routekeeper allows 15 seconds to set up a tunnel (TCP, TLS and the handshake with the proxy), or 10 seconds during a check. Open tunnels are checked with TCP keepalive: after 30 seconds of silence, three probes 10 seconds apart. A tunnel whose server has gone away is closed after about a minute.

How to add a proxy

The quickest way is to paste a proxy line. If you don’t have a line, fill in the fields by hand.

  1. In the Routekeeper window, open the Proxy section (⌘4).
  2. Click + below the list of proxies or the + (Add Proxy) button in the toolbar, which shows only an icon. ⌥⌘N does the same from any section. Empty fields open on the right.
  3. Fill in the fields as shown in the table below. If you have a rented server but no proxy yet, click Your Own Server… in the toolbar (the server icon) instead: Routekeeper sets up a proxy on the server and adds it, see Your own proxy server.
  4. Click Check. You can check before you save: Routekeeper uses what’s in the fields. What the result means is explained in Checking.
  5. Click Add. The proxy appears in the list on the left, and Routekeeper checks it again right away.

On first launch, the same is on the welcome screen: the Add a proxy server step, with the Paste from Clipboard and Enter Manually… buttons.

FieldWhat to enter
NameAny name you’ll see in the route menu: “Amsterdam”, “Office”. If you leave the field empty, the server address becomes the name.
TypeSOCKS5, HTTP or HTTPS. How to choose: see above.
ServerA domain name like proxy.example.net or an IP address like 203.0.113.10; IPv6 works too. No https:// and no port. For HTTPS, only a domain name: the certificate is checked against it.
PortThe proxy’s port, a number from 1 to 65535. If you leave the field empty, Routekeeper uses the default port for the type: 1080, 8080 or 443. The hint in the field shows which one.
LoginIf the proxy lets you in without a password, leave it empty.
PasswordSaved only together with a login.
DNS through proxyOn by default. Usually you don’t need to change it. What it does: see below.
Block UDP and QUICOn by default. Usually you don’t need to change it.

To change a proxy, select it in the list, edit the fields and click Save. Revert Changes brings back the saved values. The Used in rules: N line below the Check button shows how many routes and rules go through this proxy.

Details: where the password is stored

The password is stored by the Routekeeper network extension in its settings file. Only the system (root) can read this file. The Routekeeper window doesn’t get the saved password: the Password field shows dots instead, and the extension itself runs the proxy check. If you don’t touch the field, the password stays the same when you save. If you clear Login, the password is deleted.

Paste a proxy line

Providers and the server install script give you a proxy as a single line. Routekeeper reads it by itself.

  1. Copy the proxy line (⌘C).
  2. Paste it into Routekeeper:
    • The Proxy section: click the list of proxies on the left and press ⌘V, or click Paste below the list.
    • The welcome screen: at the Add a proxy server step, click Paste from Clipboard.
  3. A new proxy opens with the fields filled in. Check the type, server, port and login, click Check, then Add. Nothing is saved until you click Add.

Which lines Routekeeper understands:

LineTypeLogin and password
socks5://user:pass@203.0.113.10:1080SOCKS5user and pass
socks5h://203.0.113.10:1080, socks://203.0.113.10:1080SOCKS5none
http://proxy.corp.example:3128HTTPnone
https://user:pass@proxy.example.net:443HTTPSuser and pass
203.0.113.10:1080SOCKS5none
203.0.113.10:1080:user:passSOCKS5user and pass
user:pass@203.0.113.10:1080SOCKS5user and pass
socks5://[2001:db8::1]:1080SOCKS5, IPv6 address in square bracketsnone
  • The port is required, even in an https:// line. The line https://proxy.example.net without :443 won’t be recognized.
  • Without a prefix (socks5://, http://, https://), you get SOCKS5. If your provider gave you an address:port line for an HTTP proxy, change Type to HTTP after you paste it.
  • Special characters in the login and password can be written as %40 instead of @ or %3A instead of :. Routekeeper decodes them.
  • Spaces and line breaks at the start or end and a slash at the end don’t get in the way.
  • The name of a pasted proxy is the server address. You can change it in the Name field.

If the clipboard doesn’t hold a proxy line, Routekeeper replies: “The clipboard has no proxy string. Expected something like socks5://user:pass@host:1080”. The Copy Address item in a proxy’s context menu copies back only address:port, without the login and password.

Details: socks5 and socks5h

In other programs, the h in socks5h:// means “the proxy looks up site names”. In Routekeeper, both prefixes give the same SOCKS5. Whether the proxy gets names is decided by the DNS through proxy toggle, and it’s on for a pasted proxy.

DNS through proxy and UDP blocking

Each proxy has two toggles: DNS through proxy and Block UDP and QUIC. Both are on by default, including for a pasted proxy. They apply to connections that go through this proxy.

DNS through proxy

When an app opens a site by name, Routekeeper gives the proxy the name, for example example.com, not the IP address your Mac found. The proxy looks up the site’s address itself, through its own DNS.

This way, the site opens at an address that suits the server’s location: big sites give out different addresses in different countries. And if your network’s DNS answered with a wrong address, the proxy still finds the right one.

This works only when the name is known. If an app connects to an IP address by itself, the proxy gets the IP. For more about connections without a name, see Rules.

When to turn it off. When the names you need are known only to the DNS of your local or work network, and the proxy is outside that network. For example, internal company sites that open only from the office network: a remote proxy won’t find them. With the toggle off, Routekeeper gives the proxy the address your Mac found. In all other cases, keep the toggle on.

Details: what your network’s DNS sees

A connection reaches Routekeeper when the app already knows the server’s address. If macOS itself looked up the name, its query went to your network’s DNS before Routekeeper saw the connection. The toggle decides which address the proxy opens the site at, but it doesn’t cancel that query. How DNS works in Routekeeper, and how a browser can look up names over a secure channel, is explained in How it works and DNS over HTTPS in the browser.

Block UDP and QUIC

SOCKS5, HTTP and HTTPS proxies carry only TCP. UDP is a different kind of traffic: it’s used by QUIC in browsers, by voice and video calls, and by games. UDP can’t go through the proxy.

  • The toggle is on (the default). UDP connections of apps that go through this proxy are blocked. Browsers then switch to regular HTTPS over TCP, and that goes through the proxy. Sites open as usual.
  • The toggle is off. UDP from these apps goes direct, around the proxy, with your real IP. Each such connection is flagged in the Leaks section as UDP around the proxy.

The toggle doesn’t block DNS queries (ports 53 and 853): without them, apps would stop working. Such queries go direct and are flagged in Leaks as DNS around the proxy.

When to turn it off. When it matters more that calls work than that they go through the proxy. For example, a messenger goes through the proxy, and its calls use UDP: with blocking, they won’t connect at all; without it, they go direct. The toggle applies to all apps on this proxy. To leave the others as they are, add the same server again under a different name, turn off blocking only for this copy, and choose the copy as the messenger’s route. Calls over UDP don’t work through a proxy in any case; see Limitations.

Details: when the toggle applies

The toggle is checked for a UDP connection that, by the rules, should go through this proxy: by the app’s route, by a service or by a rule. Connections to ports 53 and 853 are let through directly and flagged “DNS around the proxy”, unless a separate rule has already blocked them. The rest of the UDP is blocked or, with the toggle off, let through directly and flagged. The toggle doesn’t affect UDP from apps that don’t go through the proxy. For example, a browser’s QUIC without a site name follows the browser’s own route; see Rules by site name.

Checking

The Check button opens a connection through the proxy to the ipinfo.io service and asks which IP address it sees. After a couple of seconds, the result appears next to the button, for example:

Working · 640 ms · IP 203.0.113.10 (NL)
  • IP is the address that sites see. If it matches your server’s address, the proxy works.
  • The country code in parentheses is where this address is registered, according to ipinfo.io.
  • Milliseconds is the time it takes to open a new connection through the proxy. That takes several exchanges with the server, so a healthy server far away shows 500–800 ms. In Overview, a time of 1500 ms or more is marked “slow”.

In the list of proxies on the left, each proxy has a colored dot and a short line: green means it works (SOCKS5 · 640 ms · NL), red means unreachable, blue means checking…, gray means not checked.

You don’t need to click Check every time. Routekeeper checks proxies by itself: after you save; when you open the Proxy section, if a proxy hasn’t been checked yet; and, for the main proxy, when you open the menu of the menu bar icon and after the network changes. While the main proxy isn’t answering, it’s rechecked once a minute. To check all proxies at once, use the Check All button in the toolbar.

If the check fails, a message appears instead of the result. Monitor shows the same messages for connections that couldn’t be made through the proxy.

A proxy on your own server

A proxy that Routekeeper set up with the Your Own Server… wizard gets a Server block at the bottom of its card. Routekeeper logs in to the server with its own key from the keychain, does one thing and logs out.

ButtonWhat it does
Check ServerFinds out whether the proxy is running on the server, when the certificate expires and how many addresses fail2ban is blocking. Caddy renews the certificate itself, a month before it expires.
Reinstall or Update ServerRuns the installation again with the same domain. This fixes a stopped proxy and brings Caddy and the settings up to the version in this Routekeeper. The login and password don’t change.
More → Change Proxy Password…Creates a new login and password on the server and saves them in this proxy right away. Routes and rules stay on it. If this proxy is set up anywhere else, the old password stops working there.
More → Turn Off Password Logins to the Server…The server starts accepting only keys for SSH. See Password logins to the server.
More → Save SSH Key…Saves the private key Routekeeper logs in to the server with to a file. With it you can log in to the server from Terminal: ssh -i file root@IP.
More → Remove Proxy from the Server…Removes Caddy, the certificate, the login and the password on the server. The server and everything else on it stay. In the dialog you choose whether to delete the proxy in Routekeeper too.
More → Forget Server…Routekeeper deletes its key for this server and stops managing it. The proxy keeps working on the server and in Routekeeper; the Server block disappears.

If the block shows an error, the What to do about it link under it leads to the right part of Your own proxy server.

With password logins to the server off, Routekeeper’s key may be the only one the server accepts. Forget Server… and deleting the proxy delete this key from the keychain, so save it first: More → Save SSH Key….

Several proxies

You can add as many proxies as you like. Each app, service and rule chooses its own: the route menu has a Through Proxy section with all proxies by name. For example, the browser goes through “Amsterdam”, and the work messenger through “Office”. How to choose a route is described in An app’s route.

If two proxies have the same name, the menu adds the type and port to them. It’s clearer to give them different names.

The main proxy

The main proxy is the one that most enabled routes and rules go through. If there are none, the first proxy in the list is the main one. The main proxy:

  • is shown in the panel at the bottom of the window’s sidebar, with its response time and country, and in the menu of the menu bar icon, with its external IP and country;
  • becomes the route of new apps and services;
  • is offered in the quick actions in Monitor.

A number like “+1” next to it in the sidebar means that some rules go through other proxies.

Deleting a proxy

Select the proxy in the list and click − below the list, or press Delete. You can also right-click the proxy and choose Delete…. Routekeeper asks you to confirm and tells you how many rules go through this proxy. Deleting can’t be undone: ⌘Z won’t bring the proxy back, and its login and password are deleted with it.

Routes and rules that went through the deleted proxy are turned off.

If the Your Own Server… wizard set up the proxy, the dialog has two buttons: Delete, Also from the Server removes the proxy from the server and then deletes it in Routekeeper; Delete Only from Routekeeper leaves the proxy running on the server, and Routekeeper forgets the server and its key.

A turned-off rule has no effect. Apps that went through the deleted proxy will follow the other rules and the mode. In Proxy Only mode, this means they go direct, with your real IP, and these connections won’t show up in Leaks. So first move the routes to another proxy, and only then delete.

Switching to another proxy

When a proxy stops working, or you’re moving to another server, you can move routes all at once, without changing each app. You need at least two proxies for this.

WhereWhat is moved
Overview → Routes → the ⋯ button in the proxy’s row → Move Routes ToOnly this proxy’s routes and rules.
Overview → the row of a proxy that isn’t answering → Move to “…”Only this proxy’s routes and rules. Routekeeper suggests a proxy that answered at the last check.
The panel at the bottom of the sidebar → the Proxy row → Move all apps toAll enabled routes and rules that go through any proxy.
The menu of the menu bar icon → Proxy for all appsThe same as in the sidebar. The list appears in the menu only when there are two or more proxies.
  1. Choose the proxy to move to.
  2. Routekeeper asks: Move to “…”? The question says what will move and from where. If the rules went through different proxies, Routekeeper warns that this split will be lost. It also warns you if the chosen proxy didn’t answer at the last check. Click Move. In the menu of the menu bar icon, the question appears right in the menu.
  3. After the move, a line like “5 rules moved” and an Undo button appear for 10 seconds. The button returns the moved rules to their previous proxies. Later, ⌘Z in the Routekeeper window does the same.

Only enabled routes and rules with the Through Proxy action are moved. Direct, Block and turned-off rules stay as they were. Connections that are already open stay on the previous proxy until the app reconnects.

If the proxy is down

By default, connections that should go through the proxy are dropped when the proxy fails. The app shows an error or “no network”, but connections don’t go direct, and your real IP isn’t revealed.

What you’ll see:

  • in Overview, the heading “Proxy ‘…’ is unreachable”, or “Partly working” if other proxies with routes are working;
  • in Routes, the proxy’s row turns orange: “Not responding” and “What goes through this proxy can't connect now. It doesn't go out directly.”, with the Move to “…” and Check Again buttons next to it;
  • in the menu of the menu bar icon, an orange line “Proxy ‘…’ is unreachable”, if the main proxy has failed.

What to do: move the routes to another proxy, as described above, or wait. The main proxy is rechecked once a minute. As soon as the server answers, new connections go through it again.

If it matters more to you that apps work than that they go through the proxy, turn on Settings → Network → If the proxy is down, go direct. It’s off by default. With this setting, a connection that couldn’t go through the proxy goes direct: sites see your real IP. Monitor shows these connections as direct, and they won’t show up in Leaks. A ready-made scenario is in the recipe The proxy stopped answering.

Details: what a failure looks like to the app

Routekeeper accepts the app’s connection right away and connects to the proxy at the same time. This way, browsers don’t open extra backup connections. If the proxy fails or doesn’t answer within 15 seconds, the app’s connection is dropped. With the “go direct” setting, Routekeeper connects to the site’s address itself at that moment. UDP blocking doesn’t depend on the proxy’s state.

Local client: sing-box, Xray, Clash

If you already use a client such as sing-box, Xray, Clash or a program based on them, Routekeeper can send chosen apps into it. The client still keeps the connection to your server over its own protocol, and Routekeeper decides which apps go into the client.

App → Routekeeper → SOCKS5 127.0.0.1 → client → your server → site
  1. In the client’s settings, find the local proxy port. It may be called SOCKS port, mixed port or inbound, for example 1080 or 7890.
  2. In the client, turn off the system proxy (System Proxy, Set as system proxy) and TUN mode (TUN mode, Enhanced mode, VPN mode). With the system proxy, apps go to the client by themselves, and Routekeeper no longer controls them. TUN captures all of the Mac’s traffic, like a VPN, and gets in Routekeeper’s way; see Limitations.
  3. In Routekeeper, add a proxy: Type SOCKS5, Server 127.0.0.1, Port the client’s port. You usually don’t need a login and password. You can copy and paste the line socks5://127.0.0.1:7890 with your own port in it.
  4. Leave both toggles on. With DNS through proxy, the client gets site names and looks up addresses according to its own settings.
  5. Click Check. The IP in the result should be your server’s address, not your home one.
  6. Choose the apps that will go through the client: Apps and services.

Don’t send the client itself through the proxy. Its connection to the server would come back to it, making a loop, and everything on this proxy would stop working. If you have the rule “Any App · any address → Through Proxy”, add the client to Apps with the Direct route: a rule for a specific app wins over a rule for any app; see Which rule wins.

In Ask and Block All modes, the client must be explicitly allowed to connect to the server. Add it to Apps with the Direct route, or answer Allow with the Forever duration in the prompt. Otherwise, the client’s connection to the server will be blocked or will wait for an answer, and all apps on this proxy will be left without a network. In Proxy Only and Silent modes with default settings, you don’t need to do anything. More about modes: Firewall modes.

If the client is off or has frozen, apps on this proxy are left without a network, and they don’t go direct. A ready step-by-step setup is in the recipe On top of sing-box, Xray or Clash.

Details: localhost, UDP and the client’s HTTP port
  • Connections to the address and port of any proxy in the list always go direct; rules don’t apply to them. Connections to 127.0.0.1 and ::1 are covered by built-in rules; see The list of rules.
  • Through SOCKS5, Routekeeper passes only TCP, even if the client supports UDP. So the Block UDP and QUIC toggle is needed here too.
  • If the client offers only an HTTP port, choose the HTTP type. A mixed port accepts both SOCKS5 and HTTP.

Work proxy

In an office, the IT department usually gives you the proxy: an address, a port (often 3128 or 8080) and maybe a login and password.

  1. Add a proxy: Name “Office”, Type HTTP, Server and Port from the IT department, Login and Password if needed. Choose the HTTPS type only if the IT department said the proxy accepts TLS.
  2. Click Check. If the answer is “The HTTP proxy answered 403 …”, read the item about port 80 below.
  3. Decide what will go through the work proxy:
    • whole apps, for example a work messenger: the “Office” route in Apps;
    • company addresses from any app: the rule “Any App · *.corp.example → Through Proxy ‘Office’” in Rules. For internal networks, add a rule with a subnet, for example 10.0.0.0/8. Such a rule wins over an app’s route: the browser goes through your usual proxy, and company sites through the office one.

Limitations:

  • Only login-and-password sign-in (Basic). Windows sign-in (NTLM, Kerberos, Negotiate) isn’t supported. Such a proxy answers “HTTP: the proxy requires authentication (407)”.
  • PAC files and automatic proxy discovery (WPAD) aren’t supported. If your company hands out settings in a PAC file, open the file in a browser and find a line like PROXY proxy.corp.example:3128, or ask the IT department for the address. Move the addresses that the PAC file sends to the proxy into rules.
  • Tunnels only. Routekeeper opens a tunnel (CONNECT) through an HTTP proxy for any connection, including to port 80. Many office proxies allow tunnels only to port 443. Then HTTPS sites work, but HTTP sites and the Check button get “The HTTP proxy answered 403 …”.
  • With HTTP, the login and password travel in plain text. Inside an office network, that’s usually acceptable. Over the internet, use an HTTPS proxy.

A ready-made scenario is in the recipe Work proxy for internal addresses.
